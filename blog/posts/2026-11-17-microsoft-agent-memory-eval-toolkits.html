What Microsoft Needs to Build Next: Agent Memory, Eval APIs, and True Toolkit Integration

AR Akhil Reddy Danda · 17th November, 2026 · 2 min read

Microsoft’s Copilot, GitHub, and Azure AI are table stakes in 2026—but as an engineer, I want more. Specifically, I want what Anthropic, Google, and even smaller labs are shipping: open agent memory, eval-first APIs, and composable toolkits. Here’s why the Redmond stack needs these—yesterday.

Agent Memory APIs

Anthropic’s Claude and Google’s Gemini now expose simple, project-scoped memory APIs. Their agents recall past code reviews, feedback, and user stories—context that spans sessions. Microsoft’s Copilot and Azure OpenAI? Still chat-centric, with no persistent, queryable memory. As a dev, I lose history every time I swap repos or restart a session. Microsoft should ship an open Agent Memory API—secure, exportable, and integrated with VSCode and Teams. This would make Copilot actually collaborative, not just context-parsing.

Eval-Driven Development

Eval-driven dev isn’t optional anymore. Claude and Gemini agents now take your pytest or Jest suite and iterate until green, using built-in eval harnesses. GitHub Copilot X has some test-gen features, but no first-class eval loop API for CI/CD. If Microsoft wants devs to trust AI, they need pluggable eval APIs—think "upload your harness, see the agent debug, get traceable diffs." That’s how you shift from "auto-complete" to "auto-ship".

Toolkit Protocols and Sandbox Integration

Finally, Microsoft should embrace open toolkit protocols. Anthropic’s MCP and Google’s ToolUse let agents securely invoke shell, editors, or custom plugins with minimal friction. Windows and Azure could expose secure sandboxes for agent tools—think "run this code, get structured output, never leave the VM." Engineers want to wire up agentic workflows, not just prompt monologues.

Bottom line: If Microsoft wants to keep leading, they should ship these features now. Don’t let the best open dev tools be outside the Microsoft stack.
