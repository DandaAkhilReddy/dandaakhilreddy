What Microsoft Should Steal Next: Memory APIs, Open Agent Protocols, and Eval-First Dev

AR Akhil Reddy Danda · 12th November, 2026 · 2 min read

Let’s be blunt: If Microsoft wants Copilot, Azure, and Foundry to stay relevant to the next wave of AI engineers, it needs to rapidly adopt what Anthropic, OpenAI, and Google are already shipping. The most urgent gaps? Memory APIs for agents, open agent/server protocols, and truly eval-first developer tooling.

Why Memory APIs Matter

Anthropic’s Claude Code and Google’s latest agent stacks actually give developers first-class APIs to store, retrieve, and “reason over” context—think long-running agent memory, not just big prompts. Microsoft has the infra (Azure Tables, Cosmos DB, etc), but there’s no simple, open API for Copilot or GitHub agents to persist, recall, and act on earlier work. Without this, agents remain toy copilots, not real collaborators.

Open Agent Protocols are the New Standard

Both OpenAI GPTs and Anthropic’s MCP tool servers support open JSON-based protocols for tool calling and eval. Microsoft, by contrast, has kept Copilot’s extensibility locked behind private APIs. If devs can’t plug in their own tools, test harnesses, and evals, they’ll migrate to wherever they can. Open protocols also mean better interoperability across clouds and platforms—something Azure should lead, not follow.

Eval-First Developer Experience

Serious teams start with evals—period. Microsoft needs to build (and open-source) ultra-simple eval runners for Copilot, Synapse, and GitHub workflows. Let me define my evals, run them against agent outputs, and see failure modes. It’s what modern AI engineers demand, and it’s the only way to build trust in agentic workflows. The labs have shown the way; Microsoft needs to catch up or get left behind.
